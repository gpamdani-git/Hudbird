# Anti-slop audit 001

Date: 2026-11-04
Scope: Hudbird documentation homepage, `LandingBuilderShowcase`, homepage copy, theme behavior,
and CLI delivery.
Mode: AFTER

The implementation candidate passed its required build, interaction, responsive, theme, and CLI
checks before this audit. The findings below have not been fixed. Select the finding numbers you
want changed before the delivery gate is run again.

## Findings

### 1. HIGH · Human / semantic structure · The homepage has more than one level-one heading

Evidence: the root hero renders its headline as an `h1`. `LandingBuilderShowcase` then renders a
complete `HeroSection`, which renders the same content as another `h1` inside the same document.

Why it matters: the mini builder is a demonstration inside the homepage, not a second document.
Multiple identical page titles weaken the heading outline for screen-reader and keyboard users and
make the repeated preview harder to distinguish from the real page.

Recommended change: add a preview heading-level option to `HeroSection` or supply a semantic
preview mode that renders the builder headline as `h3` while preserving its visual style.

Status: pending owner approval.

### 2. MEDIUM · Human / assistive technology · Variant changes may announce too much content

Evidence: `MotionCrossfade` receives `aria-live="polite"` around the entire hero preview. Selecting a
variant can expose a headline, paragraph, two actions, image alternative text, and caption to the
live region at once.

Why it matters: a visual crossfade should not turn a small layout choice into a long screen-reader
announcement. The selected tab already communicates the state change.

Recommended change: remove the live region from the whole preview and use a concise visually
hidden status such as `Split preview selected` only when additional feedback is needed.

Status: pending owner approval.

### 3. MEDIUM · UI / product proof · The workflow media is a generated product representation

Evidence: `hudbirdProductImage()` creates SVG representations of Compose, Sections, and Source.
The interactive hero and mini builder are real React UI, but the three AI-to-source media panels are
not captures of the current builder and exported source.

Why it matters: the page promise is strongest when every proof surface reflects the actual product.
Generated representations can drift from the builder and make the workflow feel conceptual.

Recommended change: replace the three SVG representations with maintained light and dark captures
of the real builder states and exported React source, with a small capture/update procedure.

Status: pending owner approval.

### 4. MEDIUM · Copywriting / product truth · The brand-brief step is ahead of the current builder UI

Evidence: the homepage says `Give Hudbird the brief` and asks for logo, color, purpose, content, and
reference. The current page builder exposes brand controls and composition controls, but not a
complete guided brief intake for all of those inputs.

Why it matters: the copy reads as a capability available after clicking the CTA. If the destination
does not collect the full brief, the first product interaction does not fully match the promise.

Recommended change: either add the guided brief intake to the builder or label this step as the AI
workflow and link to instructions that show how the brief is supplied.

Status: pending owner approval.

### 5. MEDIUM · Code / distribution · The public block installation includes homepage demo payload

Evidence: `LandingBuilderShowcase/demo.ts` contains the full Hudbird homepage content plus three
large inline SVG data assets. Because the registry installs every source file in the component
folder, `npx hudbird-ui add LandingBuilderShowcase` copies this demo payload into a consumer project.

Why it matters: source ownership is useful, but consumers installing one reusable block should not
receive homepage-specific content and large demo assets unless they request an example.

Recommended change: keep the block API and minimal types in `LandingBuilderShowcase`; move the
Hudbird homepage fixtures into docs or a separate optional registry entry such as
`LandingBuilderShowcaseDemo`.

Status: pending owner approval.

### 6. LOW · UI / copy rhythm · The primary hero message repeats in the next section

Evidence: the page opens with `Give AI a system to build from.` The mini builder immediately renders
the same headline, description, and two actions inside its preview.

Why it matters: repetition is useful to prove content persistence, but the current sequence asks the
visitor to read the same message twice before reaching system anatomy. The demo can retain the same
brand and content contract without repeating every call to action at full emphasis.

Recommended change: keep the shared content visible but use shorter preview copy or visually label
the duplicated text as the controlled content fixture.

Status: pending owner approval.

### 7. LOW · Code / theme ownership · Homepage theme state duplicates documentation theme logic

Evidence: `LandingPage.tsx` owns `useHomepageTheme`, while the documentation header has a separate
theme implementation. Both update the root class and `localStorage.theme`, but their default and
system semantics are maintained independently.

Why it matters: two implementations can drift, especially when storage keys or system-theme
behavior change. The homepage currently follows the requested system-first behavior, while the
documentation header still has its own default rules.

Recommended change: extract one shared docs theme controller and let the homepage supply only its
Hudbird `Button` presentation.

Status: pending owner approval.
